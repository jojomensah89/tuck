# Clipboard dictation delivery

Final text and review Insert use the same Windows Ctrl+V transaction. Focus changes during recording are allowed. The field checked for password status is the field focused at delivery; its window/control is rechecked immediately before submitting the shortcut. The existing bounded modifier wait and cancellation mutex remain. No Enter is sent. Existing event/status names, including Inserted and Copied, remain compatible; Inserted means the paste shortcut was submitted, not that the destination confirmed its contents.

The native Windows implementation preserves transferable global-memory clipboard formats (including text, HTML, DIB images and file lists) without a new dependency. Synthetic bitmap/palette handles are skipped when DIB pixels are available. GDI/owner-display/private handle formats, unreadable data and over-budget snapshots are unsupported: like Hex, paste proceeds and the previous contents are not restored. Snapshot bytes and transcript intermediates are zeroized on drop. Snapshots are bounded to 128 formats, 64 MiB per format and 256 MiB total.

Each write advances a restore generation and records GetClipboardSequenceNumber. Rapid consecutive pastes retain the original pre-dictation snapshot; stale restore workers stand down. Restoration checks the sequence while holding the Windows clipboard open, so another app cannot write between the check and restore. Both dictation and restore writes share a suppression mutex/sequence with Tuck's history reader. Dictation writes set ExcludeClipboardContentFromMonitorProcessing, CanIncludeInClipboardHistory=0 and CanUploadToCloudClipboard=0 before publishing text. Third-party history tools may disregard these cooperative Windows markers.

Missing foreground, Tuck's process, detected Edit/RichEdit ES_PASSWORD and UI Automation password fields copy without paste or restore. Modifier timeout also leaves the text copied. Clipboard preparation errors retain review text, without a second automatic copy that could overwrite a concurrent user copy. Partial shortcut submission disables retry and releases the synthetic keys. No original app is activated. Remote Desktop clients mstsc/msrdc get Hex's 400 ms pre-paste and 3 s restore delays; other apps use about 500 ms restore.

## Evidence boundaries

- Automated: frontend unit/build/UI smoke; native format/lint/unit and integration checks. New tests use policy/state seams and never access the real clipboard.
- Screenshots: regenerated by src/tests/ui-smoke.mjs using mock native dictation events, not live dictation. Dictation recording, processing, review, done, copied and cancelling states are fixtures.
- Not hardware verified: microphone dictation, real cross-app paste (Notepad/browser/Electron/elevated apps), clipboard format restoration, rapid dictation races with real apps, password detection, Shift shortcut timing, nonactivating Insert clicks, Win+V exclusion, cloud exclusion, Remote Desktop timing.
- The installed Tuck app and Hex checkout were not modified or stopped. No release or merge.
